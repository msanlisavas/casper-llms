# CSPR.name: registering, renewing and resolving .cspr names

Verified against cspr-name-contracts 2026.06.23 on 2026-09-12.

CSPR.name is the naming service for the Casper Network: a `.cspr` name is an NFT, and a separate resolver contract maps the full domain to an `Address` — an account **or** a contract — so the name and the thing it points at are two different pieces of state ([name_token.rs#L13-L21](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/name_token.rs#L13-L21), [resolver.rs#L43-L48](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/resolver.rs#L43-L48); the client's own docstring for that argument reads "address of the account/contract of cspr.name resolution (starts with either `account-hash-...` or `hash-...`)", [default-resolver.ts#L16-L23](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/client-js/src/default-resolver.ts#L16-L23)). Names are registered and resolving today — two facts with two different requests behind them. Registration: `https://api.cspr.name/domains/satoshi.cspr`, fetched on 2026-09-12, returns a name token carrying `"block_height": 5168099` and `"timestamp": "2025-07-16T17:27:46Z"` whose owner's primary name is `titan.cspr`. Resolution is a different endpoint and a different name: `https://api.cspr.name/resolutions/titan.cspr` answered HTTP 200 on 2026-09-12 with `"resolved_hash": "d9533e447dc81222d463f6b75295d9ef0264888d53b3dac6145770c6cf36af22"`, `"is_primary": true`, `"is_root": true` and `"expires_at": "2027-07-16T18:00:00Z"` (`alice.cspr` likewise, to `1856e4a0…deec`). `satoshi.cspr` is registered but does **not** resolve: `https://api.cspr.name/resolutions/satoshi.cspr` answered HTTP 404 `{"error":{"code":"not_found","message":"cspr.name not found"}}` the same day. Which chain all of this is on, and on what evidence, is set out under *Deployed addresses the website published on 2026-09-12* below — no page fetched for this guide uses the word "mainnet" about CSPR.name. You sign and submit a registration transaction yourself, but you cannot assemble one alone: the repository's example has the buyer sign the transaction and put it to a node ([onchain_purchase.ts#L42-L56](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/client-js/examples/onchain_purchase.ts#L42-L56)), while the `Controller` contract's `buy` entry point mints only after it verifies a signature made by the operator's configured signer key over the payment voucher — in that same example the voucher is signed with the admin keypair ([controller.rs#L69-L75](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/controller.rs#L69-L75), [controller.rs#L226-L233](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/controller.rs#L226-L233), [onchain_purchase.ts#L28-L34](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/client-js/examples/onchain_purchase.ts#L28-L34)). So buying goes through [cspr.name](https://cspr.name/) and a wallet ([casper.network: Casper 101 - How to Name Your Casper Account](https://www.casper.network/get-started/casper-101-how-to-name-your-casper-account)). Prices on 2026-09-12 were 250 CSPR/year for five characters or more, 750 for four and 5,000 for three, stated on that marketing page and returned in motes by the live CSPR.name API. Reading a name from software is the one part with real documentation: CSPR.cloud indexes resolutions and exposes `GET /cspr-name-resolutions/{name}` ([docs.cspr.cloud: Get CSPR.name resolution](https://docs.cspr.cloud/rest-api/cspr-name-resolution/get-cspr-name-resolution)).

Two kinds of source appear below and they are not equally durable. Contract behaviour is pinned to commit [`e193c699`](https://github.com/make-software/cspr-name-contracts/tree/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78) of `make-software/cspr-name-contracts` (Apache-2.0, the repository's newest commit, dated 2026-06-23; it publishes no releases and no tags). Prices, the grace period the website advertises, and every live API response were read on **2026-09-12** and can change the next day without a commit anywhere — they are dated in the text wherever they appear.

## What a CSPR.name is

- A name is a token in the `NameToken` contract, an Odra module that wraps the `Cep95` NFT submodule and adds a whitelist, a max supply and a **contract-level** default resolver ([name_token.rs#L1-L21](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/name_token.rs#L1-L21)). It adds an expiration check too, but that lives in `is_token_valid` ([name_token.rs#L165-L175](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/name_token.rs#L165-L175)), and the resolver recorded *per token* lives in the token's own metadata, not in the contract struct ([data_structures.rs#L23-L30](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/data_structures.rs#L23-L30)).
- The suite declares six contracts to build: `Registrar`, `NameToken`, `Controller`, `DefaultResolver`, `SecondaryMarket` and `ReverseResolver` ([Odra.toml](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/Odra.toml)). Which of them are deployed is a separate question; three package hashes the website publishes are listed further down.
- The token id is derived from the *label* only — the part before `.cspr` — as `U256::from(env().hash(label))` ([token_id.rs#L12-L15](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/token_id.rs#L12-L15)). The JavaScript client reaches a number arithmetically and hands it over as a `U256`: it folds a `byteHash` digest most significant byte first (`tokenID = (tokenID << BigInt(8)) + BigInt(tokenIdBytes[i])`) and passes `token_id: CLValue.newCLUInt256(tokenID)` ([default-resolver.ts#L90-L118](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/client-js/src/default-resolver.ts#L90-L118)). That the two agree is stated by neither source — the contract's half turns on `U256::from`'s byte order, which is not in the cited lines — but it is checkable against the token ids the live API reports, and it checks out. On 2026-09-12, `int.from_bytes(blake2b(label, digest_size=32), 'big')` reproduced exactly the `token_id` the live API reports for all six names checked — `titan` → `40304531516750293316642767216587371180187550498735645097637790547452199339302`, and likewise `satoshi`, `alice`, `xyz`, `hello` and `unitedstates` — while hashing the full domain (`titan.cspr`) instead of the label reproduced none of the six. So the digest is Blake2b-256 of the bare label read big-endian — and the client's `cleanup(domainName, …)` argument, documented as "domain name of a given token", yields a different id if it is handed a full domain.
- Token metadata is **up to** four key/value pairs: `asset_uri`, `expiration`, `name`, and `resolver` only when one is set — `to_vec` pushes the `resolver` pair inside an `if let Some(...)`, so three pairs is reachable ([data_structures.rs#L23-L30](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/data_structures.rs#L23-L30), [data_structures.rs#L67-L76](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/data_structures.rs#L67-L76)). A live token shows all four. Fetching `https://api.cspr.name/domains/satoshi.cspr` on 2026-09-12 returned them at `data.name_token.onchain_metadata` — three levels down, **not** at the top of the response — as `{"asset_uri": "https://cspr.name/token.png", "expiration": "1911751200000000", "name": "satoshi", "resolver": "hash-2c41427f79cc69456a9ad38e8cb379cb0f1084f17c467b17ccb389346fd2c139"}`.
- Only the last label before `.cspr` is the token. `odra.cspr`, `aaa.odra.cspr` and `ss.aaa.odra.cspr` all resolve through the single token named `odra`, and a domain that does not end in `.cspr` is not a CSPR.name at all ([utils.rs#L3-L14](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/utils.rs#L3-L14), [utils.rs#L95-L112](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/utils.rs#L95-L112)).

### What a valid name looks like

The registrar validates a label with the RFC 952/1123 LDH rule: 1–63 bytes, ASCII letters, digits and `-`, first and last character alphanumeric, and the label may be neither `cspr` nor contain a dot ([utils.rs#L22-L74](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/utils.rs#L22-L74), [registrar.rs#L298-L300](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L298-L300)). On three probes the live service answered as the contract's rule would: on 2026-09-12, `https://api.cspr.name/domains/-bad.cspr` answered HTTP 400 `{"error":{"code":"invalid_input","message":"name has invalid characters"}}`, a 64-character label answered HTTP 400 `"name must be between 1 and 63 characters"`, and the same label cut to 63 characters answered HTTP 200. Three inputs establish a length bound and a character class, not the whole rule — and the service demonstrably does not apply the whole rule. The label `cspr` is one the Registrar rejects outright, reverting `TokenNameIsNotValid` (1208) ([utils.rs#L72-L74](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/utils.rs#L72-L74), [registrar.rs#L298-L300](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L298-L300), [registrar.rs#L336](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L336)); `https://api.cspr.name/domains/cspr.cspr` nevertheless answered HTTP 200 on 2026-09-12, quoting `"annual_fee": "750000000000"` and flagging the name `"is_protected": true` — the same condition the price section below records. What the three probes show is the operator's own web service validating its input; it says nothing about which Wasm is deployed on chain, and as `cspr.cspr` demonstrates, a web front end and a contract can disagree.

## Registering a name

The user-facing steps, from the Casper 101 page (HTML only, no machine-readable version; fetched 2026-09-12):

1. "Go to cspr.name and use the search bar to look up the name you want." The page says the result is one of **Buy now**, **Make offer** or **Contact us**, the last meaning "The name is either protected or shorter than 3 characters and requires special handling."
2. Purchase: pick a duration, then "Sign the transaction with your Casper Wallet". The page warns to "Make sure your wallet has some extra CSPR to pay for the transaction costs."
3. Assign: go to [My names](https://cspr.name/my-names), "Select the name you wish to assign to your account", "Enter the **public key** of the account you want to link it to", and confirm. The page makes assignment a step of its own after purchase, and on chain the two are separate calls to separate contracts: `Controller::buy` mints the token, `DefaultResolver::set_resolution` points the name at an address ([controller.rs#L69-L75](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/controller.rs#L69-L75), [resolver.rs#L88-L115](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/resolver.rs#L88-L115)).

On chain, a purchase is one call to the `Controller`:

- `buy(voucher: PaymentVoucher, signature: Bytes)` is `#[odra(payable)]`. It rejects the call if the contract is paused, processes the voucher, then calls `controller_register` on the `Registrar` ([controller.rs#L69-L75](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/controller.rs#L69-L75)).
- Processing a voucher means three checks in order: the caller must be the voucher's `buyer` (`BuyerMustBeCaller`, 1104), the signature must verify against the Controller's stored signer public key (`InvalidSignature`, 1101), and the attached CSPR must equal the voucher amount exactly — less reverts `InsufficientPayment` (1105), more reverts `PaymentTooLarge` (1106) ([controller.rs#L192-L233](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/controller.rs#L192-L233), [controller.rs#L236-L246](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/controller.rs#L236-L246)).
- The payment is transferred to a treasury address the admin sets, and a `PaymentFulfilled` event carries `payment_id`, `buyer` and `amount` ([controller.rs#L205-L224](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/controller.rs#L205-L224)).
- `controller_register` requires the caller to hold `CONTROLLER_ROLE`, refuses an expired voucher (`VoucherExpired`, 1204), then for each name checks the new expiration is not earlier than block time, validates the label, and mints with the NameToken's default resolver already recorded in the metadata ([registrar.rs#L176-L181](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L176-L181), [registrar.rs#L289-L323](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L289-L323)).
- The voucher carries everything the mint needs: `PaymentInfo { buyer, payment_id, amount }`, a list of `NameMintInfo { label, owner, token_expiration, asset_uri }`, and a `voucher_expiration` ([data_structures.rs#L147-L190](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/data_structures.rs#L147-L190), [data_structures.rs#L223-L241](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/data_structures.rs#L223-L241)).
- The repository's example does not call `buy` directly. It reads `proxy_caller.wasm` from disk, passes the bytes to the `Controller` constructor, and builds the `buy` call through that ([onchain_purchase.ts#L23-L48](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/client-js/examples/onchain_purchase.ts#L23-L48)). The example gives no reason for the indirection, and this guide did not find one published.

There is no `casper-client` command for registering a name, and this guide does not invent one: without an operator-signed `PaymentVoucher` the call reverts with `InvalidSignature`, so registration is effectively UI-only. UI-only means the *voucher* has to come from the operator, not that the purchase happens off chain — the buyer still signs and submits the transaction, and the operator's own runtime config says that flow is switched on: `https://cspr.name/config.c35d9d28.js` on 2026-09-12 built both `onchain_purchase_flow_disabled` and `make_offer_flow_disabled` from the literal expression `'false' === 'true'`, so both are `false`. Several names can be bought, renewed, or bought and renewed in a single voucher-bearing call (`buy_and_renew`) ([controller.rs#L85-L101](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/controller.rs#L85-L101), [Buy and Renew a cspr name.md](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/docs/sequence-diagrams/Buy%20and%20Renew%20a%20cspr%20name.md)).

The Registrar also carries admin-only entry points that bypass the Controller and its payment entirely. `admin_register` is the one that **mints** — it asserts the caller is admin, then calls the internal `register`; `admin_prolong` **renews** rather than minting, and `admin_prolong_and_register` does both ([registrar.rs#L144-L165](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L144-L165)). That is the path the repository's fiat diagram takes: `d3 -> d3: process fiat payment`, then `d3 -> Registrar: admin_register(Vec<NameMintInfo>)` ([puml/offchain-multiple-purchase.puml](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/docs/sequence-diagrams/puml/offchain-multiple-purchase.puml)). Whether cspr.name offers a fiat option today is not something this guide verified.

## Prices as published on 2026-09-12

The Casper 101 page lists these tiers verbatim under "Note that prices vary by length". The right-hand column is the `annual_fee` field, in motes, returned by `https://api.cspr.name/domains/<name>.cspr` on 2026-09-12 for the names shown.

| Name length | Casper 101 page | Live `annual_fee` (motes) | Names checked |
| --- | --- | --- | --- |
| 5+ characters | `250 CSPR/year` | `250000000000` | `casper`, `satoshi`, `alice`, `hello`, `cspr1`, `crypto` |
| 4 characters | `750 CSPR/year` | `750000000000` | `abcd`, `make`, `odra`, `test`, `john` |
| 3 characters | `5000 CSPR/year` | `5000000000000` | `xyz`, `bob` |
| Under 3 characters | `custom pricing` | `250000000000`, with `"is_protected": true` | `a`, `ab` |

"A single CSPR consists of 1,000,000,000 motes" ([docs.casper.network: glossary, M](https://docs.casper.network/concepts/glossary/M)), so the first three rows agree exactly. The bottom row does not: the API returns the base fee for one- and two-character names but flags them `"is_protected": true`, while the 101 page says "Names shorter than 3 characters are priced individually and may not be available for public sale". For a protected name the two sources therefore disagree, and no page read here says which governs. Protection is not only about length — `casper.cspr`, `make.cspr`, `odra.cspr`, `faucet.cspr`, `crypto.cspr` and `cspr.cspr` all came back `"is_protected": true` on 2026-09-12 while being unregistered.

These are prices a website published on one day, not protocol constants. Nothing in the contracts knows a price: the amount is whatever the operator signed into the `PaymentVoucher`, and the Controller only checks that the attached CSPR equals it ([controller.rs#L205-L216](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/controller.rs#L205-L216)).

## Renewal, expiry, grace and the pending-delete period

A name passes through four states, separated by its `expiration` and by the two windows that follow it. They are not interchangeable: the name stops working long before anyone else can take it.

| Window | Boundary | What changes |
| --- | --- | --- |
| Live | `block_time <= expiration` | `is_token_valid` is true: the name resolves, and it can be transferred |
| Grace | `expiration < block_time <= expiration + grace_period` | The name stops resolving and stops being transferable, but renewal still works |
| Pending delete | up to `expiration + grace_period + 5 days` | Renewal reverts, and the name still cannot be re-registered by anyone else |
| Gone | `block_time > expiration + grace_period + 5 days` | `expire()` burns it, and `register` will burn-and-remint it for a new buyer |

- `is_token_valid` returns false the moment `expiration < block_time` — before the grace period is considered at all ([name_token.rs#L165-L175](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/name_token.rs#L165-L175)). The Registrar's `resolve` returns `None` for an invalid token, so an expired name stops resolving immediately ([registrar.rs#L91-L101](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L91-L101)).
- Renewal goes through the Controller exactly as a purchase does: `renew(voucher: RenewalPaymentVoucher, signature)` verifies and collects payment, then calls `controller_prolong` ([controller.rs#L77-L83](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/controller.rs#L77-L83)). A `RenewalPaymentVoucher` carries `TokenRenewalInfo { token_id, token_expiration }` entries rather than labels ([data_structures.rs#L244-L266](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/data_structures.rs#L244-L266)).
- `prolong` reverts with `GracePeriodExpired` (1203) once `block_time > expiration + grace_period` ([registrar.rs#L209-L215](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L209-L215)), and with `ExpirationDateInThePast` (1201) when the new expiration is **earlier than** block time — the test is `if token_expiration < block_time`, so an expiration equal to block time passes ([registrar.rs#L217-L221](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L217-L221)). `prolong` calls both ([registrar.rs#L265-L287](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L265-L287)).
- A name only becomes re-registrable when `block_time > expiration + grace_period + PENDING_DELETE_PERIOD`, where `PENDING_DELETE_PERIOD` is a hard-coded 5 days in milliseconds. Try sooner and `register` reverts with `TokenNotExpired` (1202) ([registrar.rs#L20-L23](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L20-L23), [registrar.rs#L253-L263](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L253-L263), [registrar.rs#L310-L318](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L310-L318)). The repository's own tests walk exactly these boundaries ([registrar.rs#L616-L680](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L616-L680)).
- `expire(token_ids)` is a public entry point — it carries no role check, so anyone may call it (it does require the Registrar not to be paused), and it burns only the tokens that are already past the whole window ([registrar.rs#L107-L115](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L107-L115), [expire-domain.puml](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/docs/sequence-diagrams/puml/expire-domain.puml)).
- `grace_period` is not a constant. The Registrar initialises it to `0`, an admin can change it, and the only hard bound is `MAX_GRACE_PERIOD`, 365 days ([registrar.rs#L20-L23](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L20-L23), [registrar.rs#L63-L66](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L63-L66), [registrar.rs#L116-L126](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L116-L126)). The deployed value is not published anywhere this guide could read; what *is* published is the website's own runtime config, which on 2026-09-12 told its UI `cspr_name_renewal_grace_period: '720h'` — 30 days — at `https://cspr.name/config.c35d9d28.js`. That is the operator's advertised figure, not a value read from chain state.
- The Casper 101 page's whole account of renewal is one sentence: "You can renew it before expiration, or let it lapse."

### Expiration timestamps are microseconds in production

The metadata `expiration` of a live name is a microsecond timestamp, not milliseconds: `satoshi.cspr` returned `"expiration": "1911751200000000"` on 2026-09-12, which is 2030-07-31T18:00:00Z read as microseconds. The contracts handle this explicitly — the stored value is kept verbatim and `trim_microseconds_to_milliseconds_if_needed` divides anything above 99,999,999,999,999 by 1,000 on read, so every comparison against block time happens in milliseconds ([utils.rs#L76-L91](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/utils.rs#L76-L91), [data_structures.rs#L78-L87](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/data_structures.rs#L78-L87)). The getter's own doc comment says so: the stored value "is kept verbatim as the off-chain component provides it (which may be microseconds), so this getter normalizes on read", and "the raw stored value is only ever serialized back via `to_vec` / `json`, preserving metadata units" — which is why the metadata a reader sees is the un-normalized one. CSPR.cloud does not expose that raw value at all; it publishes `expires_at` as a formatted timestamp string ([docs.cspr.cloud: CSPR.name resolution](https://docs.cspr.cloud/rest-api/cspr-name-resolution)).

## Resolution: pointing a name at an account

- Each token's metadata names the resolver contract that answers for it; minting records the NameToken's default resolver ([name_token.rs#L143-L157](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/name_token.rs#L143-L157), [registrar.rs#L301-L306](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L301-L306)). The owner can point the token at a different resolver with `set_resolver` ([name_token.rs#L149-L157](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/name_token.rs#L149-L157)).
- `DefaultResolver::set_resolution(full_domain, address)` stores the mapping. It reverts unless the token is valid (`ResolutionSetWithInvalidToken`, 1401), the caller owns it (`ResolutionSetByInvalidOwner`, 1402) and the whole domain passes label validation (`InvalidSubdomainFormat`, 1406) ([resolver.rs#L88-L115](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/resolver.rs#L88-L115), [resolver.rs#L158-L167](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/resolver.rs#L158-L167)). Passing `None` as the address removes the resolution ([default-resolver.ts#L62-L88](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/client-js/src/default-resolver.ts#L62-L88)).
- Resolutions are keyed by `(token_id, full_domain, nonce)`, and `invalidate_resolutions(token_id)` simply increments the nonce, orphaning every mapping under that token at once ([resolver.rs#L43-L48](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/resolver.rs#L43-L48), [resolver.rs#L127-L139](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/resolver.rs#L127-L139)).
- Because subdomains resolve through the parent token, one name can hold many mappings: `odra.cspr` and `docs.odra.cspr` are separate resolution keys under the same token ([resolver.rs#L141-L145](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/resolver.rs#L141-L145)). The repository's tests use exactly that pair — `MAIN_DOMAIN = "odra.cspr"`, `SUBDOMAIN = "docs.odra.cspr"` ([resolver.rs#L179-L180](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/resolver.rs#L179-L180)) — resolving each to a different address and then watching both vanish together when the token's resolutions are invalidated ([resolver.rs#L357-L376](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/resolver.rs#L357-L376)).
- Subnames are a shipped feature of the product, not only a property of the contracts. The cspr.name front-end bundle declares a page route `path:"/subnames/:tokenId"` and navigates to it from a "Subnames" button — ``onClick:()=>g(`/subnames/${t.token_id}`)`` — and the list behind that page is an API read of ``yW(`name-tokens/${a}/resolutions`, …, {is_root:!1})``, which the bundle's paging helper turns into `GET /accounts/{account_hash}/name-tokens/{token_id}/resolutions` (`https://cspr.name/static/js/main.2558081f.js`, read 2026-09-12). `/subnames/{token_id}` is that page route and not an API route: on 2026-09-12 `https://api.cspr.name/subnames/40304531…` answered HTTP 404 with the generic body `404 page not found`, while `https://api.cspr.name/accounts/d9533e44…af22/name-tokens/40304531…/resolutions?is_root=true` answered HTTP 200 `{"item_count":1,"page_count":1,"data":[…]}` carrying `titan.cspr`, and the same request with `is_root=false` answered `{"item_count":0,"page_count":0,"data":[]}`. The UI's own copy in that bundle reads "You can create as many subnames (e.g., `subname.name.cspr`) as you like. Each subname must be assigned to an account. You can reassign or delete your subnames at any time." — which matches the contracts: a subname is a resolution key under the parent token, so "delete" is `set_resolution` with `None`, not a burn.
- A contract can resolve a name on chain: `Registrar::resolve(full_domain)` extracts the label, checks the token is valid, then asks that token's resolver, returning `Option<Address>` ([registrar.rs#L91-L101](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/registrar.rs#L91-L101), [Resolution.md](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/docs/sequence-diagrams/Resolution.md)). The Controller exposes the same call ([controller.rs#L103-L106](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/controller.rs#L103-L106)).

## Primary names and reverse lookup

A name pointing at an account is forward resolution. The reverse — an account announcing which name should be displayed for it — is a separate contract and a separate transaction.

- `ReverseResolver::set_primary_name(primary_name)` stores `caller -> name`, but only after checking that the name already resolves **to the caller**: if there is no resolution it reverts `ResolutionForPrimaryNameNotFound` (1501), and if the resolution points elsewhere it reverts `InvalidResolutionAddress` (1502) ([reverse_resolver.rs#L29-L58](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/reverse_resolver.rs#L29-L58), [reverse_resolver.rs#L6-L11](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/reverse_resolver.rs#L6-L11)).
- Ownership is deliberately *not* required. The Casper 101 page says the same thing in user terms: "Even if someone else assigns a name to your account, you can still choose to set it as your primary, ownership of the name isn't required to display it." The contract check is on the resolution, not on `owner_of` ([reverse_resolver.rs#L73-L84](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/reverse_resolver.rs#L73-L84)).
- `get_primary_name` re-checks the resolution every time, so a primary name silently disappears if the underlying resolution is cleared or the token expires ([reverse_resolver.rs#L60-L71](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/reverse_resolver.rs#L60-L71)).
- In the UI: "Go to the name's page in your dashboard", "Click 'Make Primary'", "Sign the transaction with your wallet" (Casper 101 page, fetched 2026-09-12). The underlying entry point is `set_primary_name` with a single `primary_name` string argument ([reverse-resolver.ts#L23-L48](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/client-js/src/reverse-resolver.ts#L23-L48)).
- Reverse lookup works today: on 2026-09-12 both `https://api.cspr.name/domains/titan.cspr` and `.../satoshi.cspr` reported the same owner account hash `d9533e44…af22` with `"owner_cspr_name": "titan.cspr"`, and CSPR.cloud documents `owner_cspr_name` as "Primary CSPR.name of the owner account" ([docs.cspr.cloud: Non-fungible token](https://docs.cspr.cloud/rest-api/non-fungible-token)).

## Trading a name

Names are NFTs, so they trade like NFTs — but the expiry rules bite.

- Trading is live. Casper announced it on **19 November 2025**: "You can now: Make offers for CSPR names that are already taken; Buy names listed for sale at a fixed price; Sell your own CSPR names directly on CSPR.market" ([casper.network: CSPR Names Are Now Tradable on CSPR.market](https://www.casper.network/news/cspr-names-are-now-tradable-on-cspr-market)). There is a dedicated how-to ([casper.network: Casper Guide 102 - How to Buy and Sell CSPR Names on CSPR.market](https://www.casper.network/get-started/casper-guide-102-how-to-buy-and-sell-cspr-names-on-cspr-market)), and its offer step warns that "Your offered CSPR tokens will be locked until the owner accepts or you withdraw your offer."
- Live listings exist. On 2026-09-12 `https://api.cspr.name/domains/xyz.cspr` reported `"is_listed": true` at `10000000000000000` motes (10,000,000 CSPR) and `satoshi.cspr` at `200000000000000` motes (200,000 CSPR).
- CSPR.market's own documentation covers the mechanics generically, for any NFT: listing requires a one-time approval transaction so "the market contract is given it the right to transfer the NFT (no transfer will take place unless the item is sold)", then a price and a signature; buying is a Buy button and a signature; an offer is a price and a signature, and the owner accepts from the Offers section ([docs.cspr.market: Selling your NFT](https://docs.cspr.market/selling-your-nft), [docs.cspr.market: Buying an NFT](https://docs.cspr.market/buying-an-nft)).
- **An expired name cannot be sold or transferred at all.** `transfer_from` and `admin_transfer` both revert with `ExpiredTokenTransfer` (1303) when `is_token_valid` is false, which happens the instant `expiration < block_time` — so the grace period is a window in which a name can be renewed but not traded ([name_token.rs#L104-L134](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/name_token.rs#L104-L134), [name_token.rs#L242-L251](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/name_token.rs#L242-L251), [Secondary-sale market.md](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/docs/sequence-diagrams/Secondary-sale%20market.md)).
- **A sale looks likely to wipe the name's resolutions.** When a transfer is made by someone other than the token's owner, `NameToken::cleanup` resets the token's resolver to the default resolver and calls `invalidate_resolutions`, so the recipient gets a name that points nowhere and has to set a resolution again. A marketplace sale fits that branch on the face of it — CSPR.market's own listing step exists to give "the market contract … the right to transfer the NFT", so the market contract, not the seller, is the caller — but this guide did not trace an actual sale transaction to confirm it ([name_token.rs#L121-L134](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/name_token.rs#L121-L134), [name_token.rs#L230-L239](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/name_token.rs#L230-L239)). Neither the 102 guide nor CSPR.market's documentation mentions this.
- Fees and royalties on a CSPR.market sale are not documented on any page this guide read.

## Reading a name from software

CSPR.cloud's REST API is the documented read path, and it needs an access token: "The access token should be included in the `Authorization` header" ([docs.cspr.cloud: Authorization](https://docs.cspr.cloud/documentation/overview/authorization)). The operator's own `https://api.cspr.name/resolutions/{name}` answers the same question with no key at all — but nothing documents it, so it is described under *The undocumented API the website itself uses* below rather than recommended here.

- `GET /cspr-name-resolutions/{name}` returns one resolution. The documented example, with its sample token replaced by `<access key>`, is `curl -X 'GET' 'https://api.testnet.cspr.cloud/cspr-name-resolutions/faucet.cspr' -H 'Accept: application/json' -H 'Authorization: <access key>'` ([docs.cspr.cloud: Get CSPR.name resolution](https://docs.cspr.cloud/rest-api/cspr-name-resolution/get-cspr-name-resolution)). The page documents no query parameters, no sorting, no optional properties and no status codes.
- The `CSPRNameResolution` entity has five documented properties ([docs.cspr.cloud: CSPR.name resolution](https://docs.cspr.cloud/rest-api/cspr-name-resolution)):

| Property | Type | Meaning |
| --- | --- | --- |
| `name_token_id` | `string` | ID of the name token (NFT) |
| `name` | `string` | Name, for example `cloud.cspr` |
| `resolved_hash` | `string(64)` | Account hash as a hexadecimal string |
| `is_primary` | `boolean` | Whether this is the account's single primary name |
| `expires_at` | `string` | Resolution expiration timestamp |

  Depending on the endpoint it may also carry `resolved_public_key`, `account`, `account_info`, `centralized_account_info` and `name_token`.
- For the reverse direction, CSPR.cloud says that when you want "to resolve account hashes to the corresponding CSPR.name names, in most of the cases it's possible to do by requesting CSPR.name as optional property in the `includes` query parameter", and recommends the direct resolution endpoint instead "for the situations when you receive the name outside CSPR.cloud" ([docs.cspr.cloud: Resolving CSPR.name](https://docs.cspr.cloud/documentation/highlights/resolving-cspr-name)). `?includes=cspr_name` on `GET /accounts/{key}` adds the account's primary name; `?includes=caller_cspr_name` on a deploy adds the caller's; NFT endpoints expose `owner_cspr_name` and `cspr_name_resolutions` ([docs.cspr.cloud: Account](https://docs.cspr.cloud/rest-api/account), [docs.cspr.cloud: Non-fungible token](https://docs.cspr.cloud/rest-api/non-fungible-token)).
- The API was added in CSPR.cloud 1.4.0 on 2024-08-19 ("Added CSPR.name resolution API") and reverse resolution in 1.4.5 on 2024-10-22 ("Added reverse resolution for CSPR.name") ([docs.cspr.cloud: Changelog](https://docs.cspr.cloud/documentation/changelog)).
- Appending `.md` to a docs.cspr.cloud or docs.cspr.market URL returned the page as markdown for every page this guide cites. The sites say so themselves, in a banner carried at the top of each markdown page: "Markdown versions of documentation pages are available by appending `.md` to page URLs." Both also publish an `llms.txt` index — [docs.cspr.cloud/llms.txt](https://docs.cspr.cloud/llms.txt), [docs.cspr.market/llms.txt](https://docs.cspr.market/llms.txt).

### The Resolution API described in the contracts repository

The repository's diagrams describe a "Resolution API" that takes `/resolve full_domain`, reads the token metadata over RPC, checks the expiry, extracts the resolver address and reads the mapping — answering `200 address`, `404 record not found` when there is no mapping, or `404 token expired` when the block time is past the expiry ([resolve-name.puml](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/docs/sequence-diagrams/puml/resolve-name.puml)). This is a design in a sequence diagram. No public host serving it was found: on 2026-09-12 `https://api.cspr.name/resolve?full_domain=casper.cspr`, `/api/resolve`, `/v1/resolve`, `/resolve`, `/names/casper.cspr` and `/` all answered HTTP 404 with the body `404 page not found`.

### The undocumented API the website itself uses

`https://api.cspr.name` — `api_url` in the site's runtime config — answers unauthenticated and is the source of most of the live figures in this guide. It is **not documented anywhere**. Its routes were read out of the cspr.name front-end bundle (`https://cspr.name/static/js/main.2558081f.js`, 4,281,247 bytes, fetched 2026-09-12), which makes its HTTP calls through a single client. The calls below are the ones found by reading that client's call sites; the bundle is 4.3 MB of minified code, so treat the list as what was found rather than as a complete inventory. The right-hand column says which this guide actually sent on 2026-09-12:

| Call as it appears in the bundle | Exercised here |
| --- | --- |
| ``get(`/domains/${e}`)``, and a ``get(`/domains/${e}`, {params:n})`` variant whose parameters were not established | yes — availability, price, ownership and marketplace state |
| ``get(`/resolutions/${e}`, {params:{includes:"account_info,centralized_account_info,resolved_public_key"}})`` | yes — with and without the `includes` |
| ``get(`/accounts/${r}`, {params:{includes:"account_info,centralized_account_info,cspr_name"}})`` | yes |
| ``get(`/accounts/${t}/${e}`, {params:{page, page_size, …}})``, where `${e}` is `name-tokens` or ``name-tokens/${token_id}/resolutions`` | yes, both |
| ``get(`/rates/${r}/latest`)`` | yes |
| ``post(`/domains/${r}/payment-vouchers`, {buyer_key:n, annual_periods:i})`` | no |
| ``post(`/domains/${r}/renewal-payment-vouchers`, {buyer_key:n, annual_periods:i})`` | no |
| ``post(`${config.api_url}/wasm-proxy-transaction`)`` | no |
| ``post(`${config.api_url}/wasm-proxy-transaction-submission`)`` | no |
| ``post("/domain-interest-contact-request", e)`` — the request behind the "Contact us" route this guide describes for protected names | no |

Nothing published documents any of this, versions it, or commits the operator to keeping it. Two POST routes are named for the signed vouchers the `Controller` verifies, and two for submitting transactions — the naming and the request bodies are the only evidence of what they do — so none of the four was sent here. What the five GETs answered on 2026-09-12:

- `/resolutions/{name}` is the one that proves a name resolves. For `titan.cspr` and `alice.cspr` it answered HTTP 200 inside a `data` envelope holding `expires_at`, `is_primary`, `is_root`, `name`, `name_token`, `name_token_id`, `resolved_hash` and `updated_at`; for `satoshi.cspr` and `casper.cspr`, HTTP 404. The `includes` query parameter is honoured: adding the bundle's three values put `account_info`, `centralized_account_info` and `resolved_public_key` into the same object.
- `/accounts/{account_hash}` answered HTTP 200 with `account_hash`, `balance`, `deployment_threshold`, `genesis_balance`, `key_management_threshold`, `main_purse_uref` and `public_key` — a plain account read, with no name in it until `includes=…,cspr_name` adds `"cspr_name": "titan.cspr"`.
- `/accounts/{account_hash}/name-tokens` and `/accounts/{account_hash}/name-tokens/{token_id}/resolutions` answered HTTP 200 in a **different** envelope from every other route here: `{"item_count":…,"page_count":…,"data":[…]}`, paged by `page` and `page_size`. For `d9533e44…af22` the first reported `"item_count": 5`.
- `/rates/cspr/latest` answered HTTP 400 ``{"error":{"code":"invalid_input","message":"Invalid `currency_id` format"}}`` — the backticks are the service's own. Whatever a `currency_id` is, it is not a ticker, and nothing published says what it is.
- Errors come back as `{"error":{"code":…,"message":…}}`, with `invalid_input` on 400 and `not_found` on 404 among the codes. A path the service does not route answers differently again — plain text `404 page not found`, no JSON — so an ingester can tell a missing record from a missing route.
- A bare label is normalised to `<label>.cspr`: `https://api.cspr.name/domains/casper` returned the `casper.cspr` body, `"name":"casper.cspr"` included.
- The `includes` values in the bundle (`account_info`, `centralized_account_info`, `cspr_name`, `resolved_public_key`) are the same vocabulary CSPR.cloud documents for its own endpoints. Nothing read here says the two services share an implementation; treat the overlap as an observation, not a guarantee that CSPR.cloud's documentation describes this API.

On 2026-09-12, for a registered name, the whole `/domains/{name}` response sat inside a `data` envelope holding five keys: `annual_fee`, `is_protected`, `name`, a `cspr_market_listing` object (`contract_package_hash`, `is_listed`, `price`, `token_id`) and a `name_token` object. The `name_token` object's own keys were `block_height`, `contract_package_hash`, `cspr_name_resolutions_count`, `cspr_name_root_resolution`, `is_burned`, `offchain_metadata`, `offchain_metadata_status`, `onchain_metadata`, `owner_account_info`, `owner_centralized_account_info`, `owner_cspr_name`, `owner_hash`, `owner_public_key`, `owner_type`, `timestamp`, `token_id`, `token_standard_id` and `tracking_id`. What any of them mean is not published: `block_height` and `timestamp`, for instance, might describe the mint or might describe the last indexed update, and nothing read here says which. Two of them are actively misleading if read at face value. `titan.cspr` returned `"cspr_name_resolutions_count": 0` and `"cspr_name_root_resolution": null` on 2026-09-12 — the same day and the same name for which `/resolutions/titan.cspr` returned a live root resolution — so neither field can be read as "this name does not resolve"; ask `/resolutions/{name}` instead. And a `cspr_market_listing` object is not evidence that a name exists: `hello.cspr` came back with `"name_token": null` (unregistered) and a listing stub all the same, `{"contract_package_hash":"50d4d8cf…","is_listed":false,"price":null,"token_id":"2275311838…"}`, the `token_id` being the Blake2b-256 of `hello` whether or not anything has been minted. `name_token: null` is the registration signal, not on its own an availability signal: a protected name returns `name_token: null` too (`casper.cspr`, `make.cspr` and `cspr.cspr` all did on 2026-09-12), so read `is_protected` with it.

## Corrections: published pages that are out of date

Three statements on pages an assistant is likely to have ingested are wrong as of 2026-09-12.

### 1. CSPR.cloud says CSPR.name "is not launched yet"

[docs.cspr.cloud: Resolving CSPR.name](https://docs.cspr.cloud/documentation/highlights/resolving-cspr-name) still reads, verbatim:

> At the moment of writing this page (August 27th, 2024), the CSPR.name is not launched yet. That's why we added a test CSPR.name for the Faucet account to allow developers to implement and test their CSPR.name integration before the launch.

The sentence is two years old and the page carries it in the current documentation version as well as in the archived [1.5.x](https://docs.cspr.cloud/1.5.x/documentation/highlights/resolving-cspr-name.md) and [1.4.x](https://docs.cspr.cloud/1.4.x/documentation/highlights/resolving-cspr-name.md) sets. CSPR.name is launched. The strongest and most independent evidence is Casper's own newsroom: on [19 November 2025](https://www.casper.network/news/cspr-names-are-now-tradable-on-cspr-market) it announced buying, selling and offers as shipped, and the naming flow has its own [Casper 101 guide](https://www.casper.network/get-started/casper-101-how-to-name-your-casper-account) with live prices. Two further signs, weaker because both come from the operator's own undocumented API and were read on one day (2026-09-12): `https://api.cspr.name/domains/satoshi.cspr` returns a name token for an account hash `d9533e44…af22` whose primary name is `titan.cspr`, and `xyz.cspr` and `satoshi.cspr` both carry `"is_listed": true`. The `faucet.cspr` example on the CSPR.cloud page is still a testnet fixture — note its `"expires_at": "2124-08-27T12:00:00Z"` on that page, a year-2124 placeholder — and should not be read as a live name.

### 2. The Casper 101 page says secondary sales are not available

The same page that carries the live price table still says, in its Step 1 list of search results:

> **Make offer**: The name is already owned by someone else and is listed on CSPR.market. (Secondary sales are not yet available)

and closes with "Secondary sales and trades will be available via cspr.market, stay tuned for announcements." Casper's own newsroom contradicts this from [19 November 2025](https://www.casper.network/news/cspr-names-are-now-tradable-on-cspr-market), Casper publishes a [102 guide](https://www.casper.network/get-started/casper-guide-102-how-to-buy-and-sell-cspr-names-on-cspr-market) devoted to buying and selling names, and live listings exist. Secondary sales are available; the parenthesis is stale.

### 3. `expires_at` is documented as ISO 8601 and is not

[docs.cspr.cloud: CSPR.name resolution](https://docs.cspr.cloud/rest-api/cspr-name-resolution) describes `expires_at` as a "Resolution expiration timestamp in the ISO 8601 format" and then gives `"expires_at": "2124-08-27 12:00:00.00"` — a space instead of `T`, no timezone, a two-digit fraction. The same value appears in the [endpoint page](https://docs.cspr.cloud/rest-api/cspr-name-resolution/get-cspr-name-resolution)'s example, which also returns an `updated_at` field that the entity's property table does not list. Parse `expires_at` defensively rather than handing it to a strict ISO 8601 parser. (The older [highlights page](https://docs.cspr.cloud/documentation/highlights/resolving-cspr-name) shows the same name as `"2124-08-27T12:00:00Z"`, so the two pages do not agree with each other either.)

## What nobody has published

An honest refusal beats a guess. As of 2026-09-12, this guide could not verify any of the following, and nothing below should be answered from memory:

- **An API reference for `api.cspr.name`.** There is no documentation site: `docs.cspr.name` does not resolve, and every documentation-shaped path on `cspr.name` returns the same 2,407-byte single-page-application shell. Every route above was recovered from the site's own JavaScript, and four of them were not exercised here. For the two voucher routes the bundle does show the request: a POST of `{buyer_key, annual_periods}` to `/domains/{name}/payment-vouchers` and to `/domains/{name}/renewal-payment-vouchers`. What comes back, whether anything authenticates the call, and whether either route will exist next week are unknown. For `/wasm-proxy-transaction` and `/wasm-proxy-transaction-submission` even the request is opaque — the bundle posts a variable, and logs failures as "Middleware API request failed:". Unknown too are the meanings of the fields `/domains/{name}` does return: `block_height` and `timestamp` look like a mint, but no published source says whether they describe the mint or the last time the indexer touched the record, so do not report either as a registration date.
- **The WebSocket API, beyond what its own client reveals.** Nothing about it is published — no page mentions it — but the site's runtime config names it (`ws_url: 'wss://api.cspr.name'`, read 2026-09-12) and the front-end bundle shows how it is used: a connection per transaction at `wss://api.cspr.name/streaming/transactions/{transaction_hash}`, a bare `Ping` keep-alive, messages shaped `{data:{status, error_message}}`, and the client treating `status === "processed"` as terminal. That is the client's behaviour, not a documented protocol: authentication, any other stream, the full set of statuses and whether the route persists are unknown, and this guide opened no connection to it.
- **Which chain the deployed contracts are on, from a source that says so.** The cspr.name config sets `cspr_chain_name: 'casper'`, and Casper's CLI documentation says Mainnet's chain name is `casper` — that inference is set out above, and it is an inference. No operator page states the network, and this guide read nothing from chain state.
- **The deployed `grace_period`.** It is a Registrar variable, not a constant, and reading it needs an RPC this guide could not reach or an indexer key it did not have. `720h` is what the website tells its own UI, not a value read from chain state.
- **Why the repository's purchase example routes `buy` through a proxy-caller Wasm.** The example does it ([onchain_purchase.ts#L23-L48](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/client-js/examples/onchain_purchase.ts#L23-L48)) without explaining it, and no page read here explains it either.
- **The Registrar and NameToken contract package hashes as published by the operator.** The website's config lists only the Controller, default resolver and reverse resolver. The NameToken package hash quoted above comes from the undocumented API, not from a published deployment record.
- **Renewal pricing.** The live API's `annual_fee` is an annual figure for a name; whether renewal is charged at the same tier, and what happens to the price of a name whose tier changed, is not published.
- **Fee mechanics beyond the tiers.** The Controller forwards the whole attached amount to a treasury address ([controller.rs#L205-L224](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/controller.rs#L205-L224)); where that treasury sends it, and any split, discount, bulk or promotional pricing, is not published. Nor are CSPR.market's fees or royalties on a name sale.
- **Which NFT standard the indexers report.** The live API returns `"token_standard_id": 3` for name tokens, while CSPR.cloud's documented standards example lists only `1 CEP47` and `2 CEP78` ([docs.cspr.cloud: Get NFT standards](https://docs.cspr.cloud/rest-api/non-fungible-token/get-token-standards)). The contract source builds on Odra's `Cep95` module ([name_token.rs#L1-L21](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/name_token.rs#L1-L21)), but no page read here states what id 3 means.
- **A usable JavaScript client package.** `client-js` in the contracts repository is source only: its `package.json` is an unedited copy of the CEP-18 client's, declaring `"name": "casper-cep18-js-client"` and pointing at `casper-ecosystem/cep18`, and its README's whole usage section is a `# Usage` heading with `TBD` under it ([client-js/package.json](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/client-js/package.json), [client-js/README.md](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/client-js/README.md)). Do not tell anyone to `npm install` a CSPR.name client; no such package was verified to exist.
- **Anything about `SecondaryMarket`.** The contract is declared in the suite's build manifest and is 81 lines of source, but no page read here says whether it is deployed, whether it is used in production, or how it relates to CSPR.market ([marketplace.rs](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/casper-name-contracts/src/contracts/marketplace.rs), [Odra.toml](https://github.com/make-software/cspr-name-contracts/blob/e193c699b5d1b169e53e7bc0bc39cdcc33f53c78/Odra.toml)).
