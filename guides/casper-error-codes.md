# Casper execution errors: decoding ApiError codes, system-contract errors and rejected transactions

Verified against casper-node v2.2.2, casper-client-rs v5.0.1, casper-sidecar v2.1.0 and docs.casper.network 2.0.0 on 2026-09-23.

A Casper transaction can fail in two places, and each place speaks its own language. A node can refuse it at submission, before it reaches a block, and the JSON-RPC call then returns an error ([acceptor](https://github.com/casper-network/casper-node/blob/v2.2.2/node/src/components/transaction_acceptor/error.rs#L13-L55), [binary port](https://github.com/casper-network/casper-node/blob/v2.2.2/node/src/components/binary_port.rs#L1351-L1366)). Or it can be included in a block and fail during execution: its execution result then carries an `error_message`, such as `Mint error: 12` or `User error: 1` ([artifact builder](https://github.com/casper-network/casper-node/blob/v2.2.2/node/src/components/contract_runtime/types.rs#L69-L84)). This guide decodes both, from the source at the casper-node [v2.2.2](https://github.com/casper-network/casper-node/releases/tag/v2.2.2) tag, whose casper-types crate is [7.1.1](https://github.com/casper-network/casper-node/blob/v2.2.2/types/Cargo.toml#L3). Most of these numbers are defined in casper-types' [`api_error.rs`](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs) and in the error enums of the three system contracts, [auction](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/system/auction/error.rs), [mint](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/system/mint/error.rs) and [handle payment](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/system/handle_payment/error.rs). The documentation's [Execution Error Codes](https://docs.casper.network/developers/cli/execution-error-codes) page, read on 2026-09-23, has no table: of the five offset ranges it names three (payment, mint and user errors) and links to `docs.rs/casper-types/latest` ([source](https://github.com/casper-network/docs-redux/blob/34b2071b550feef46fcdbb40bb87f1a711df8958/versioned_docs/version-2.0.0/developers/cli/execution-error-codes.md?plain=1#L5-L11)), which on 2026-09-23 showed no `ApiError` reference (see [Where the sources disagree](#where-the-sources-disagree)). Every table below cites its pinned sources, and each row of the code tables links the line it came from.

## ApiError exit codes and their ranges

A contract stops with a 32-bit exit code, and `ApiError` splits the code space into ranges ([api_error.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L70-L79)):

| Exit code | Range | Inner code N | Message at v2.2.2 |
|---|---|---|---|
| 1 to 50 | [General `ApiError` variants](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L583-L632) | the exit code | `ApiError::Name [E]` |
| 64512 to 64767 | [Auction](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L31-L32) | exit code minus 64512 | `ApiError::AuctionError(Name) [E]` |
| 64768 to 65023 | [Contract header](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L28-L29) | exit code minus 64768 | `Contract header error: N` |
| 65024 to 65279 | [Mint](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L25-L26) | exit code minus 65024 | `Mint error: N` |
| 65280 to 65535 | [Handle payment](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L22-L23) | exit code minus 65280 | `Handle Payment error: N` |
| 65536 to 131071 | [User](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L34-L38) | exit code minus 65536 | `User error: N` |

- The offsets are added in [`From<ApiError> for u32`](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L633-L637), and a casper-types test pins three ranges: mint from 65,024 to 65,279, handle payment from 65,280 to 65,535 and user from 65,536 to 131,071 ([test](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L846-L854)).
- The number after `User error:`, `Mint error:`, `Handle Payment error:` and `Contract header error:` is the inner code N, not the exit code: `ApiError::User(0)` prints `User error: 0`, and its debug form prints `ApiError::User(0) [65536]` ([test](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L913-L929)).
- Only four variants print that short form; every other variant, the auction errors included, prints its debug form, which ends with the exit code in square brackets ([Display](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L800-L810), [Debug suffix](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L796)).
- A code in no range, including 0, 51 to 64511 and anything above 131071, decodes to `ApiError::Unhandled` ([`From<u32> for ApiError`](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L642-L700)), whose own code is 31, so the message reads `ApiError::Unhandled [31]` and the original number is lost ([code 31](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L613)).
- The `revert` host function turns whatever `u32` a contract passes into an `ApiError` this way ([externals.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/execution_engine/src/runtime/externals.rs#L212-L217), [revert](https://github.com/casper-network/casper-node/blob/v2.2.2/execution_engine/src/runtime/mod.rs#L3277-L3279)), and the failed execution's message is that error's display text ([`Revert`](https://github.com/casper-network/casper-node/blob/v2.2.2/execution_engine/src/execution/error.rs#L73-L75), [artifact builder](https://github.com/casper-network/casper-node/blob/v2.2.2/node/src/components/contract_runtime/types.rs#L249-L258)).

The same arithmetic in Python, for turning a raw exit code into its range and inner code; it restates the ranges above and adds nothing to them:

```python
def message_for_exit_code(code: int) -> str:
    if 65536 <= code <= 131071:
        return f"User error: {code - 65536}"
    if 65280 <= code <= 65535:
        return f"Handle Payment error: {code - 65280}"
    if 65024 <= code <= 65279:
        return f"Mint error: {code - 65024}"
    if 64768 <= code <= 65023:
        return f"Contract header error: {code - 64768}"
    if 64512 <= code <= 64767:
        return f"auction error {code - 64512}: see the auction table"
    if 1 <= code <= 50:
        return f"general ApiError {code}: see the general table"
    return "ApiError::Unhandled [31]"
```

## Why one error can read three ways

Which spelling a failure gets depends on the path it took, not on the error. The mint's `InsufficientFunds`, code 0, is a worked example:

| Path | Message | Source |
|---|---|---|
| Wasm session code whose transfer fails and that reverts with the mint's error, as casper-contract's `unwrap_or_revert` does | `Mint error: 0` | [unwrap_or_revert.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/smart_contracts/contract/src/unwrap_or_revert.rs#L20-L21), [Display](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L805) |
| A native delegation or `add_bid` whose transfer into the bonding purse fails | `Mint error: 0` | [detail.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/storage/src/system/auction/detail.rs#L897-L912), [auction.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/storage/src/system/auction.rs#L195-L200), [state/mod.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/storage/src/global_state/state/mod.rs#L1303-L1311), [tracking-copy error](https://github.com/casper-network/casper-node/blob/v2.2.2/storage/src/tracking_copy/error.rs#L32-L33) |
| A failure raised through the system-error wrapper, as in payment and refund handling | `Mint error: Insufficient funds` | [system/error.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/system/error.rs#L38), [tracking-copy error](https://github.com/casper-network/casper-node/blob/v2.2.2/storage/src/tracking_copy/error.rs#L47-L48), [handle_refund.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/storage/src/data_access_layer/handle_refund.rs#L210-L216) |
| A native transfer (Transaction V1, mint lane) | `Insufficient funds` | [state/mod.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/storage/src/global_state/state/mod.rs#L2243-L2251), [transfer.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/storage/src/system/transfer.rs#L62-L64), [mint Display](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/system/mint/error.rs#L264) |

The node also writes the words `Insufficient funds` itself when the paying purse cannot cover a transaction's cost, so that message alone does not tell the two apart ([operations.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/node/src/components/contract_runtime/operations.rs#L605-L618)).

Auction errors take one of two spellings:

- **Wasm calling the auction** (a session that calls `delegate`, say): the engine converts the auction error into a revert ([delegate arm](https://github.com/casper-network/casper-node/blob/v2.2.2/execution_engine/src/runtime/mod.rs#L1122-L1153), [reverter](https://github.com/casper-network/casper-node/blob/v2.2.2/execution_engine/src/runtime/mod.rs#L747-L767)), so the message is the debug form, for example `ApiError::AuctionError(DelegationAmountTooSmall) [64557]`.
- **Native auction transactions** (Transaction V1, auction lane): `add_bid` and `delegate` return an `ApiError` ([add_bid](https://github.com/casper-network/casper-node/blob/v2.2.2/storage/src/system/auction.rs#L71-L84), [delegate](https://github.com/casper-network/casper-node/blob/v2.2.2/storage/src/system/auction.rs#L308-L314)) and read the same way, while `activate_bid`, `withdraw_bid`, `undelegate`, `redelegate`, `change_bid_public_key`, `add_reservations` and `cancel_reservations` wrap the auction error as a system error ([state/mod.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/storage/src/global_state/state/mod.rs#L1258-L1362)) and read `Auction error: ` followed by the Display text, for example `Auction error: Unbond is too large` ([system/error.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/system/error.rs#L40), [Display](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/system/auction/error.rs#L447)).
- The engine turns the three `GasLimit` variants, auction 40, mint 19 and handle payment 32, into `Out of gas error` when a system contract returns them to Wasm, so they rarely appear by number ([reverter](https://github.com/casper-network/casper-node/blob/v2.2.2/execution_engine/src/runtime/mod.rs#L752-L765), [`GasLimit`](https://github.com/casper-network/casper-node/blob/v2.2.2/execution_engine/src/execution/error.rs#L64-L66)).

## "User error: N": errors a contract defines

`User error: N` means a contract reverted with `ApiError::User(N)`, exit code 65536 + N ([range](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L637)). casper-types gives N no meaning: the contract's author chose it, usually as an enum converted into `ApiError::User`, as the type's own documentation shows ([example](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/api_error.rs#L81-L101)). The message does not say which contract reverted; the engine keeps only the `ApiError` ([`Revert`](https://github.com/casper-network/casper-node/blob/v2.2.2/execution_engine/src/execution/error.rs#L73-L75)). To decode N, find the source of the contract the transaction called, at the version that was installed, and look for the enum that converts into `ApiError::User`. The same N means different things in different contracts, as the two CEP-18 implementations below show.

**The testnet faucet.** The documentation says faucet tokens "can be requested **only once per account**. Otherwise, the deploy will fail with status `User error: 1`" ([Funding Testnet Accounts](https://docs.casper.network/users/testnet-faucet), read 2026-09-23; [source](https://github.com/casper-network/docs-redux/blob/34b2071b550feef46fcdbb40bb87f1a711df8958/versioned_docs/version-2.0.0/users/csprlive/testnet-faucet.md?plain=1#L22-L28)). On 2026-09-23 a testnet node, `https://node.testnet.casper.network/rpc`, answered `info_get_deploy` for the deploy that page links, `f0f6b25db767d1a6c2244324661d853ad7d4766f8489d81c36b5e2c9d982891e`, with a `Failure` execution result in block 1640491 whose `error_message` is `"User error: 1"` and whose `cost` is `"330023140"`. That deploy's header timestamp is 2023-04-13, more than two years before casper-node v2.0.0 was published on 2025-06-09 ([release](https://github.com/casper-network/casper-node/releases/tag/v2.0.0)), and its result is a `Version1` execution result, while a v2.2.2 node writes `Version2` results ([serde names](https://github.com/casper-network/casper-node/blob/v2.2.2/types/src/execution/execution_result.rs#L30-L37), [artifact builder](https://github.com/casper-network/casper-node/blob/v2.2.2/node/src/components/contract_runtime/types.rs#L468-L482)). It shows the message a faucet deploy got under Casper 1.x in 2023; no faucet failure under 2.x was read.

So `User error: 60003` is `Overflow` in a cep18 v1.2.0 token and `CannotTargetSelfUser` in an Odra 2.9.1 one.

**Any Odra contract.** Odra reverts every error as `ApiError::User` with the error's code ([host_functions.rs](https://github.com/odradev/odra/blob/2.9.1/odra-casper/wasm-env/src/host_functions.rs#L311-L318)). Its own framework errors use codes from 64535 up: `MaxUserError` is 64535, `UserErrorTooHigh` is 64536, and every other framework error's code is 64536 plus its enum value ([error.rs](https://github.com/odradev/odra/blob/2.9.1/core/src/error.rs#L221-L236)). At 2.9.1 those values are 1 and 2 and 100 to 137 ([error.rs](https://github.com/odradev/odra/blob/2.9.1/core/src/error.rs#L106-L194)), so an Odra contract's framework failures read `User error: 64537` (`UnwrapError`), `User error: 64538` (`UnexpectedError`) and `User error: 64636` to `User error: 64673` (`AdditionOverflow` to `PathIndexOutOfBounds`; for example `User error: 64660` is `OutOfGas`, value 124). A contract code at or above 64536 is replaced with `UserErrorTooHigh` ([error.rs](https://github.com/odradev/odra/blob/2.9.1/core/src/error.rs#L34-L42)).

## Rejected at submission: JSON-RPC errors and binary-port codes

When a node refuses a transaction, its binary port answers with a numeric `ErrorCode` and an empty payload ([binary_port.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/node/src/components/binary_port.rs#L1351-L1366), [binary_response.rs](https://github.com/casper-network/casper-node/blob/v2.2.2/binary_port/src/binary_response.rs#L31-L36)). The node's detailed reason, for example `invalid chain name: expected casper, got casper-test`, is not sent. casper-sidecar, whose RPC API server is "a JSON bridge between end users and a Casper node's binary port" ([README](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/README.md?plain=1#L162-L164)), turns the number into a fixed sentence ([node_client.rs](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/node_client.rs#L806-L944)), and what a client receives depends on the method and the code, at sidecar v2.1.0, its latest release on 2026-09-23 ([release](https://github.com/casper-network/casper-sidecar/releases/tag/v2.1.0)):

| RPC method | JSON-RPC `code` and `message` | `data` |
|---|---|---|
| `account_put_transaction`, invalid transaction | -32016, "Invalid transaction" | `the transaction was invalid: ` + the sentence in the table below |
| `account_put_deploy`, invalid deploy | -32008, "Invalid Deploy" | `the deploy was invalid: ` + the sentence |
| either, any other refusal | -32018, "Node request failure" | `request for submitting a transaction has failed: ` (or `a deploy`) + the sentence |

Sources: [error codes](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/rpcs/error_code.rs#L29-L49), [messages](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/rpcs/error_code.rs#L83-L95), [data prefixes](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/rpcs/error.rs#L12-L13), [data prefixes](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/rpcs/error.rs#L48-L51), [account_put_deploy](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/rpcs/account.rs#L90-L91), [account_put_transaction](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/rpcs/account.rs#L146-L147). casper-client 5.0.1 reports such a reply as `response for rpc-id {rpc_id} {rpc_method} is json-rpc error: {error}` ([error.rs](https://github.com/casper-ecosystem/casper-client-rs/blob/v5.0.1/lib/error.rs#L71-L80)).

### Every refusal code the transaction acceptor can return

The Code column links the variant in [`binary_port/src/error_code.rs`](https://github.com/casper-network/casper-node/blob/v2.2.2/binary_port/src/error_code.rs) at v2.2.2. The RPC code and the sentence that casper-sidecar v2.1.0 appends to the `data` prefix come from its decoding of the code ([`from_error_code`](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/node_client.rs#L806-L944), [mapping](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/node_client.rs#L569-L721)) and from the texts of its two error enums ([`InvalidTransactionOrDeploy`](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/node_client.rs#L319-L567), [`Error`](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/node_client.rs#L723-L803)). The last column is what the node itself calls the problem, from the `Display` of the matching `InvalidDeploy` ("Deploy") or `InvalidTransactionV1` ("V1") variant, or from the acceptor; it is listed so the cause can be read, and it is not in the reply. Only codes that a conversion from an acceptor error can produce are listed ([acceptor](https://github.com/casper-network/casper-node/blob/v2.2.2/node/src/components/transaction_acceptor/error.rs#L68-L128), [InvalidDeploy](https://github.com/casper-network/casper-node/blob/v2.2.2/binary_port/src/error_code.rs#L407-L463), [InvalidTransactionV1](https://github.com/casper-network/casper-node/blob/v2.2.2/binary_port/src/error_code.rs#L465-L581)).

## Where the sources disagree

- **Sidecar code 114.** casper-sidecar v2.1.0 maps binary-port code 114, `InvalidMaximumDelegationAmount`, to the sentence "Using `version` for targeting contract version is not supported" ([mapping](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/node_client.rs#L715), [text](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/node_client.rs#L561-L562)); the node means a maximum delegation amount above the chainspec's ceiling ([check](https://github.com/casper-network/casper-node/blob/v2.2.2/node/src/types/transaction/arg_handling.rs#L322-L330)).
- **Sidecar code 118.** casper-sidecar v2.1.0 is built against the casper-node v2.2.0 binary port ([Cargo.toml](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/Cargo.toml#L17-L21)), whose enum ends at 117 ([v2.2.0](https://github.com/casper-network/casper-node/blob/v2.2.0/binary_port/src/error_code.rs#L372)), so the v2.2.1 code 118, `InvalidInitiator`, arrives as "received an unexpected node error: unknown node error code (118)" ([fallback](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/node_client.rs#L939-L942), [text](https://github.com/casper-network/casper-sidecar/blob/v2.1.0/rpc_sidecar/src/node_client.rs#L763-L764), [v2.2.0 text](https://github.com/casper-network/casper-node/blob/v2.2.0/binary_port/src/error_code.rs#L389)).

## What this guide does not cover, and what nobody publishes

As of 2026-09-23 none of the following was found in the sources read for this guide, and none should be answered from memory:

- **The meaning of a `User error: N` for a contract whose source is not public.** No registry maps installed contracts to their error enums, and the message does not name the contract that reverted.
- **The cspr.live testnet faucet's error list.** The documentation ([Funding Testnet Accounts](https://docs.casper.network/users/testnet-faucet), read 2026-09-23) gives only `User error: 1` for a second request.
- **Messages observed on live 2.x failures.** No 2.x execution result was read. The one live result, the faucet deploy above, executed on 2023-04-13 under Casper 1.x. The formats for native transfers and native auction calls are derived from the v2.2.2 source, not observed.
- **Texts that wallets and explorers show.** Casper Wallet, CSPR.click, cspr.live and CSPR.cloud may rewrite or translate these messages; what each one shows was not checked.
- **casper-client's own validation errors**, printed before anything is sent, and binary-port codes that do not arise from submitting a transaction.
- **The sentences other sidecar versions return.** The rejection tables quote casper-sidecar v2.1.0; which version a given RPC provider runs is not published.
- **VM2 errors.** VM2 is off on mainnet ([`vm_casper_v2 = false`](https://github.com/casper-network/casper-node/blob/v2.2.2/resources/mainnet/chainspec.toml#L205-L207)), and its error types are not covered.
- **Error codes of other token and NFT standards** (CEP-78, CEP-95 and others) and of other contract frameworks, beyond the CEP-18 and Odra examples above.
